# Safari, Mac first

Roadmap step 6, item 23. Written 2026-11-11. Safari is a launch target, Mac before iPhone. This Mac has Xcode 26.4, `safari-web-extension-converter` and `-packager`, Kevin's Apple Development and Developer ID identities, Safari 26.5.2, and an iOS 26.4 simulator.

Nobody commits, pushes or deploys until Kevin says so. Nothing goes to App Store Connect or TestFlight without him.

## Why a spike first

Chrome runs the model in an offscreen document, because its service worker can't, and Firefox runs it in a background page, with `ort.env.wasm.proxy = true` so its memory goes away with a worker. Safari has neither an offscreen API nor, as far as anyone here knows, a way to keep a page alive. Everything else in the extension is ordinary WebExtension code. So the first job is to find where the model can run in Safari, and measure it, before building anything around it.

## Phase 1: the spike

A throwaway Safari wrapper of the current build, made with the converter into a scratch folder, signed with Kevin's Apple Development identity and run from Xcode. Nothing from it is committed except the findings.

**Where the model could run, tried in this order:**

1. **A non-persistent background page,** the same path Firefox uses, if Safari's MV3 allows `background.scripts`. Check whether a Worker can be made there, so the proxy setting works.
2. **The service worker,** running onnxruntime-web on the main thread, without the proxy, if Safari allows WebAssembly there under `wasm-unsafe-eval`. Measure what happens when Safari stops the worker after it's been idle: how long the 89 MB model takes to load again, and whether memory is freed.
3. **An extension page in a hidden frame,** if 1 and 2 fail: one page, opened on demand and closed when idle, doing what Chrome's offscreen document does.
4. **Native code in the app extension,** through `browser.runtime.sendNativeMessage` to `SafariWebExtensionHandler`, running the same ONNX model with Core ML or ONNX Runtime. Last, because it's a second code path with its own scores, and the app extension's memory is limited.

**For each path that loads, measure and record:**

- Scores against the Mac's, with `eval/browser-check.json`: `flips: 0` is what counts, as in `docs/TESTING.md`.
- Time to load the model, time per picture, and Safari's memory for the extension, from Activity Monitor's Safari Web Content and extension processes, plus Safari's own Web Inspector. Activity Monitor can hide compressed memory, so also note it after an hour of idling.
- Whether it survives Safari stopping the background, and comes back on the next picture.
- The hash: does `SlopHash` give the same hashes in Safari's extension context as the Chrome and Firefox checks? `eval/hash-check` and the synthetic fixtures already exist.

**Also check, because they decide later work:**

- Which APIs exist: `alarms`, `storage.sync`, `declarativeNetRequest` with `modifyHeaders`, `permissions`, `contextMenus`, `offscreen`, `runtime.getBackgroundPage`.
- **The headers a Safari extension's `fetch` sends to the API.** If it sends a per-install `Origin`, like Firefox's `moz-extension://<uuid>`, it has to be stripped or sending stays off, the same rule as Firefox.
- How Safari asks for site access, and what the extension sees before you allow it.
- Whether content scripts, shadow DOM bars, the hover button and `elementsFromPoint` all behave on Facebook.

**The spike ends with a short report** in this plan: which path works, the numbers, and a recommendation. Kevin decides from that before phase 2.

## Phase 2: the real build, once a path is chosen

- An Xcode project in `safari/`, made once with the converter, pointing at `dist/safari` rather than copying it, with the macOS app as the container. The app itself is one small window in the poster look, telling you how to turn the extension on in Safari's settings. Copy says "you" and "your".
- Bundle ID and team set in the project. Kevin decides whether the team ID goes in the repo, which goes public later.
- The privacy policy, README and docs updated for Safari, including anything Safari-specific about what's sent.
- Version bump.

## Phase 3: getting it to people (Kevin's steps, walked through one at a time)

- An App Store Connect app record, the App Store privacy details, and a TestFlight build for Mac, so testers get one click and automatic updates, as `docs/ROADMAP.md` "Installing before launch" says.
- Notarization isn't needed for the App Store route. A direct download outside the App Store would need it, and isn't planned.

## Decisions for Kevin

- **Price:** free, matching "free on every platform", or the earlier paid iPhone idea. The recommendation is free on Mac. The roadmap lists it as open.

## Not in this

## Changes after review (these override anything above)

A review on 2026-11-11 checked Apple's docs, release notes and WebKit bugs. Where this section and the parts above disagree, this section wins. Anything marked "reported" still has to be seen working on this Mac.

**Safari is newer than this plan assumed.** Safari 27 shipped on 14 September 2026 and runs on macOS 26. This Mac is still on 26.5.2. The **Safari 27.3 beta (3 November) adds the `offscreen` API**, the same one Chrome's design uses, so `offscreen.html` and `ensureOffscreen` may carry over almost unchanged once it ships. No shipping Safari has it yet, and when 27.3 ships isn't known. So the spike runs on both: Kevin updates this Mac's Safari to the current 27.x, and installs the 27.3 beta, if he's willing (a download, which he OKs).

**New order of places to try:**
1. **Quick pass/fail checks first,** because each one rules paths in or out:
   - Does `'wasm-unsafe-eval'` work? It was broken in Safari 18 and fixed in WebKit in April 2025, but it's not known which Safari shipped the fix.
   - Can a `Worker` be created from a non-persistent background page? A 2023 report says it couldn't.
2. **The background page with the proxy worker,** the Firefox path, if both checks pass.
3. **The offscreen document on the 27.3 beta,** the Chrome path.
4. **The service worker without the proxy.** A reported Safari 26 bug stops Web Inspector attaching to a `service_worker` background, so use `scripts` with `persistent: false` while debugging.
5. **A hidden extension page.**
6. **Native code in the app extension.**

**Measure waking up and real load.** Let Safari unload the background on its own, then send a picture check, because reported bugs say it sometimes doesn't wake. Measure memory with Facebook open and scrolling, not just at idle. Apple publishes no memory limits for either the background or the app extension, so these numbers are the only guide.

**The Origin header.** Safari's `safari-web-extension://<UUID>` reportedly changes on every Safari launch, so it can't follow you for long, but it's still extra data on the wire. Measure what a vote and a list fetch actually send. Don't reuse `origin-rules.json` and `declarativeNetRequestWithHostAccess` without seeing `modifyHeaders` work on `Origin` in Safari. If it can't be stripped, decide with Kevin, using the measured value. Firefox's `data_collection` branch stays Firefox-only.

**Site access.** Safari grants access per site, as "Always allow" or "Ask each time". Test what `permissions.contains({origins})` returns while only some sites are allowed. If it's false, voting and the crowd list would quietly stay off, and the check needs to be about `api.hidetheslop.com` alone. Also test cold-start injection on Facebook, because of `all_frames` and `document_idle`, and a fix for a related delay in 27.2.

**Other facts to plan around:**
- `storage.sync` exists in Safari but doesn't sync, so it works as local storage. Settings won't follow you between devices.
- `contextMenus` exists on Mac and not on iPhone.
- Safari ignores unsupported APIs, so a missing one fails quietly rather than with an error. Feature-check everything.

**Loading it without Xcode:** Safari Settings → Developer → **Add Temporary Extension…** takes a folder with `manifest.json`. Safari removes it after 24 hours or when you quit, and "Allow unsigned extensions" resets on quit. That's fine for the spike. Testers need a signed build.

**Distribution:** Apple's Safari extension docs mention TestFlight only for iOS and visionOS, and say to give Mac testers an unsigned "Copy App" build. Whether TestFlight for Mac works for an app holding a Safari extension, and auto-updates, has to be confirmed in App Store Connect before testers are promised one click. Notarization is only for distribution outside the App Store.

**Phase 2 build:** choose between `background.scripts` with `persistent: false` and `service_worker` based on the spike, and set `browser_specific_settings.safari.strict_min_version` to the Safari the chosen path needs. Don't assume Firefox's manifest block can be reused.

**A fourth decision for Kevin:** the minimum Safari version. If the offscreen path wins, that's 27.3, which isn't out yet.

**Who does what in the spike:** the builder converts, builds and measures. Kevin has to do the clicks only he can: updating Safari and installing the beta, turning on **Allow unsigned extensions** or enabling the signed app's extension in Safari Settings, and granting site access.

## Spike results (2026-11-11, Safari 27.2, macOS 26)

Run on this Mac with the kit in `.local/safari-spike/` (not committed), signed with Kevin's Apple Development identity, against a local server. Nothing touched the live API or Facebook.

**Quick checks (a1, background page; a2, service worker):**

| | Background page | Service worker |
|---|---|---|
| WebAssembly under `'wasm-unsafe-eval'` | Works | Works |
| `new Worker` | Works, classic and module | Not available |
| Dynamic `import()` | Works | Not allowed |
| `offscreen` | Missing | Missing |
| `alarms`, `storage.sync`, `storage.session`, `declarativeNetRequest`, `permissions`, `contextMenus`, `runtime.getBackgroundPage` | Present | — |

**The model on the background page with the proxy worker (b), Firefox's path:**
- 224 of 224 pictures scored, **0 flips** against the Mac, largest drift 0.12, which is less than Firefox's 0.27.
- About 0.27 s per picture. The model loads in 0.3 to 0.6 s once it's downloaded.
- Memory: the extension's process peaked around 530 MB while scoring 224 pictures back to back, and read about 350 MB in use just after waking.
- **Waking:** Safari unloaded the background on its own after about 3 minutes idle. An alarm then woke it, the model reloaded and scored a picture in 0.63 s. Because Safari ends the process, its memory goes with it, which is what the Firefox fix needed.
- **Hashes:** 23 of 24 synthetic fixtures identical to Chrome and Firefox, and the other within 3 bits, so Safari votes merge with theirs.

**The Origin header:** every request carried `safari-web-extension://<UUID>` at first, even with a `declarativeNetRequest` rule to remove it already enabled. After the test switched the rule off and on again with `updateEnabledRulesets`, a GET went out with no Origin and a POST with the literal `null`. So stripping works, but apparently only after the rulesets are re-enabled at runtime. Host access for `127.0.0.1` read as not granted throughout, which may matter. Not yet confirmed: whether re-enabling at startup is enough, and whether the UUID really changes every launch.

**Recommendation:** build Safari on the background page with the proxy worker, the same path Firefox uses. Skip the offscreen document (c), which only the unreleased 27.3 beta has, and the service worker (d), which can't make a worker or load code on demand. The hidden page (e) and native code (f) aren't needed. Set the minimum to Safari 27.2, the version tested.

**Seen by Kevin in the spike:** the real Settings page showed "Hide the Slop can't see any pages yet", so Safari reports no site access until you grant it, matching the host-access result above. Its wording named Firefox, which is now browser-neutral. Phase 2 must check that the **Allow on all sites** button works in Safari, through `permissions.request`.

**Still to check in phase 2:** the Origin strip with host access granted and rulesets re-enabled at startup, with nothing sent until it's confirmed; the extension on real Facebook (per-site access, cold-start injection, bars, hover button); and memory after an hour of real browsing.

### Phase 2 changes after review (these override the spec above)

**Proving the Origin strip, not hoping.** The spike saw the UUID leak while the rule was listed as enabled, so neither `getEnabledRulesets()` nor a resolved `updateEnabledRulesets` proves anything.
- Add `slopStripReady()` in `common.js`, a promise made once per background run. It disables and re-enables `strip-origin`, then sends one **canary** request and checks the reply.
- The canary goes to a new route on the website's Worker, `https://hidetheslop.com/.well-known/origin-check`. It answers only `{"extension": true|false}`, meaning whether an extension Origin arrived. It never returns the value, and stores and logs nothing. Add that host to `origin-rules.json`. The UUID can only ever reach Kevin's own site, and only on this one request.
- On Safari, `allowed()` and `listAllowed()` await `slopStripReady()` first. Start it at the top of `background.js`, before `SlopVotes.start()` and `SlopCrowd.start()`.
- If the canary shows an extension Origin, or fails, voting and the list stay off in Safari for that run. Re-arming happens again at the next background start.
- **Backstop:** add `header_up -Origin` to the API's `reverse_proxy` in the `Caddyfile`, so the API never sees an Origin from any browser. Run `scripts/local-stack.sh check`. Deploying the site route and the Caddyfile waits for Kevin's OK.

**A release gate:** a real Safari run, against the local echo server, measures the strip both with site access granted and without it. The spike never measured the granted case.

**Site access:** Safari's per-site list only includes sites you've visited, so in practice only **Allow on all websites** makes the gate true, and the content scripts need it anyway.
- Word the notice as "allow it on all websites", with Safari's own Settings → Extensions → Websites steps as the fallback.
- On Safari, drop the `.catch(() => true)` in the permission check, so a failed call doesn't read as granted.
- Test `permissions.request` from a click. If Safari wants `optional_host_permissions`, add it to the Safari target only.
- Make "Firefox needs your OK" and any other Firefox-named copy neutral where Safari can show it.

**The Xcode project:**
- Don't keep the converter's file-by-file references. Use one Run Script phase on the extension target that runs `node extension/build.mjs safari`, then `rsync -a --delete` from `extension/dist/safari/` into the extension's resources, with `ENABLE_USER_SCRIPT_SANDBOXING = NO`.
- `build.mjs` gets a way to build one target, and doesn't zip Safari.
- **Bundle IDs:** the app is `com.hidetheslop.app` and the extension `com.hidetheslop.app.extension`, lowercase. Change the extension's `PRODUCT_BUNDLE_IDENTIFIER` and `extensionBundleIdentifier` in `ViewController.swift` together. Fix the converter's `.Hide-the-Slop` app ID. Bundle IDs live in `Shared.xcconfig`, not in target settings.
- Lower `MACOSX_DEPLOYMENT_TARGET` from 26.4 to the oldest macOS that runs Safari 27, which has to be checked.
- `.gitignore`: add `safari/Local.xcconfig`, `safari/build/`, `xcuserdata/` and `DerivedData/`.

**Checks in the real Safari build:**
- `slopIsSafari()`: confirm `runtime.getManifest()` keeps `browser_specific_settings.safari`. If not, use a build-time key such as `slop_target: "safari"`.
- What `runtime.openOptionsPage()` from `onInstalled` does: a tab or a popover.
- Keeping `persistent: false` is fine, because Safari ignores it.

## Phase 2 as built (2026-11-11)

Built as the spec and review above say, with these choices, each for a reason worth knowing:

- **The canary goes when it's needed, not at startup.** `slopArmStrip()` re-arms the rule at the top of `background.js` on every start, as specified. The canary itself is sent by `slopStripReady()` the first time a vote or list download asks in that run, because Safari wakes the background for picture checks, and a request on every wake would follow your browsing. It's still once per run.
- **Two requests, not one.** The canary is a GET shaped like the list download and a POST shaped like a vote, and both must come back `{"extension": false}`. The spike saw a POST and a GET treated differently (a stripped POST carried `Origin: null`, a GET nothing), so one shape can't vouch for the other.
- **It needs access to both hosts first.** Without site access, Safari sends a CORS preflight, and DNR rules don't touch preflights, so the canary would leak the ID it's meant to catch. `slopStripReady()` checks access to `hidetheslop.com` and `api.hidetheslop.com` before sending, and a missing grant isn't remembered for the run, so allowing it later works without a restart.
- **The canary has its own rule.** Rule 2 in `origin-rules.json` matches only `https://hidetheslop.com/.well-known/origin-check`. Widening rule 1 to `hidetheslop.com` would also take `Origin` off the model download from `models.hidetheslop.com`, which a browser without site access for that host may need for CORS.
- **The site route runs only for that path** (`run_worker_first`), so the pages stay free static assets, and `observability` is off.
- **A re-read of the spike's headers:** the probe that saw no Origin had just *disabled* the `ship` ruleset, so the strip appeared with the rule off, right after a runtime ruleset change. Why isn't known. The canary doesn't depend on knowing: it measures what arrives.
- **`slopIsSafari()`** reads `browser_specific_settings.safari`, and falls back to the extension's own `safari-web-extension:` address, so a Safari that drops the key from `getManifest()` still gets Safari's checks rather than Chrome's none. The gate reports which one held.
- **"Firefox needs your OK to share"** stays: only Firefox can show it, because `slopAskToShare()` resolves yes everywhere else.
- **Minimum macOS 15.0:** Apple's Safari 27 security notes list macOS Sequoia and Tahoe.
- **The app reads its extension's ID from its Info.plist,** which gets it from `Shared.xcconfig`, so the two can't drift, and the gate can build the same project under its own IDs.
- **`scripts/local-stack.sh check` wasn't run:** its `up` builds the API image, whose `npm ci` downloads packages, and this Mac has no cached image or build cache for it. The Caddyfile change was checked instead with the cached `caddy:2-alpine`, as `docs/TESTING.md` describes.

**Waiting on Kevin:** the release gate (`.local/safari-spike/PHASE2-STEPS.md`), then deploying the website route and the Caddyfile, then real Facebook. A Safari install must not reach the live servers before the route is deployed, because until then the canary gets the static site's 404 and keeps sending off, which is safe but means Safari never sends.

## Release gate results (2026-11-12, Safari 27.2)

The real `dist/safari` build, as the GATE app, run in Kevin's Safari against local servers over about 12 hours. Nothing reached the live API or site.

- **Origin:** every real request, 18 votes, 5 list downloads and 21 checks each way, went out with no extension Origin (none on GET, the literal `null` on POST). The only requests with `safari-web-extension://<UUID>` were the deliberate raw probes while site access wasn't granted, and the build sent nothing real then. The strip holds once site access is granted.
- **Robot:** 224 of 224 scored, 0 flips, largest drift 0.12. About 2.1 s per picture when woken by an alarm, against 0.27 s in the spike. To check on real Facebook browsing.
- **Crowd:** the list downloaded, and the page hid the listed picture as "the crowd flagged it" within 3.5 s, while the unlisted one stayed visible.
- **Votes:** a rating queued and sent, and the queue emptied.
- **Settings** opens in a tab.
- **Allow on all websites does nothing in Safari:** Kevin had to grant access in Safari's Settings → Extensions. The Safari copy should lead with those steps rather than a button that can't work.
- **Safari closes the background 30 s after an alarm wakes it,** even mid-task, per WebKit's own log. Timer work has to fit in that window, so Safari's request timeouts should be shorter.
- **Build quirk:** an incremental `xcodebuild` doesn't re-sign the extension after a JS-only change. Use `clean build`.

## Real Facebook test (2026-11-12)

The real signed `Hide the Slop` app, with the robot on, in Kevin's Safari on his Facebook feed: AI pictures were hidden about as fast as in Chrome. The 2.1 s per picture in the gate came from its alarm-woken slices, not from normal browsing. The site route isn't deployed yet, so this build correctly held back voting and the list.

Fixes after the gate, done: Safari shows its own Settings steps instead of the **Allow on all websites** button; request timeouts are 6 s on Safari (`slopRequestTimeout()`); `docs/TESTING.md` says to always `clean build`.

Left for Safari: deploy the `origin-check` route and the Caddyfile backstop, then a real vote and list download from Safari; App Store Connect and how Mac testers install it (TestFlight for Mac is still unconfirmed for an app with a Safari extension); remove the spike and gate apps from this Mac.
