## What gets sent

Only when `shareRatings` is on, and only for a rating made while it's on:

- `POST https://api.hidetheslop.com/v1/votes` with `{hashVersion: 1, votes: [{phash, token, label, source}]}`.
- `POST /v1/embeddings`, only for hashes the server named in `needEmbedding`.

Never the rating's `key`, a URL, a page, or anything else. Requests use `credentials: 'omit'`, `referrerPolicy: 'no-referrer'`, a 15-second timeout and no custom headers. Ratings made before you turned it on are never sent.

## Settings

- **`shareRatings` is per install, in `storage.local`, not `storage.sync`.** It's off by default. Consent on one laptop shouldn't quietly turn sharing on for another, and Firefox's data permission is per install anyway. List the default in `SLOP_DEFAULTS` with a comment, but it needs its own handler rather than the automatic `input[data-key]` wiring, which writes to sync.
- The control goes in `options.html`, with a plain explanation of what's sent and what isn't, in "you" and "your". Below it, show how many ratings are waiting, with a **Send now** link, because Kevin needs that to test, and because it shows people what's queued.
- Turning it off clears the queue at once. `voteSecret` stays, so turning it back on keeps replacing the same votes rather than adding new ones.
- Add a short opt-in to the welcome page (roadmap item 5). Visual changes get shown to Kevin in the preview before anything's committed.

## The hash

- Add `phash.js` to `offscreen.html` and to Firefox's `background.scripts`, before `vision.js`.
- In `SlopVision.inspect()`, call `SlopHash.fromBlob(blob)` on the same blob, so it's still one download, and return `{meta, embedding, phash}`. A failure or a `null` hash must never stop the picture check.
- Hash every inspected picture rather than only rated ones, because verdict matching (step 5) needs that anyway, and the model takes far longer than the hash. Measure the added time per picture and report it.

## `extension/src/votes.js`

`var SlopVotes`, in the style of `SlopTrain`. Loaded in the service worker's `importScripts` and in Firefox's `background.scripts`. Pure parts run in Node.

- **Secret:** 32 random bytes in `storage.local` as `voteSecret`, made the first time it's needed. Never in sync.
- **Token:** first 16 bytes of `HMAC-SHA-256(secret, "hts-vote-v1:" + hashVersion + ":" + phash)`, as 32 lowercase hex digits, through `crypto.subtle`.
- **Queue:** `voteQueue` in `storage.local`, entries `{phash, label, source, e, after}`. Rating the same hash again replaces its entry. Keep at most 500, dropping the oldest.
- **Timing:** `after` is a random time 1 to 6 hours ahead, so sending doesn't follow your browsing. An hourly alarm sends what's due, which needs the `alarms` permission. **Send now** ignores `after`.
- **Batches:** at most 10 per run, shuffled, because `CROWD-API.md` says to keep batches small to limit what `xmin` can group.
- **Replies:**
  - `202`: remove the sent items, then, for each hash in `needEmbedding`, send its embedding once. A failed embedding isn't retried, because a later voter can supply it.
  - `400` or `413`: drop the batch, so one bad item can't block the queue forever.
  - `429`, `503`, `5xx` or a network failure: keep everything and try at the next alarm.
- **Quiet failure:** none of this may affect hiding or rating, and it logs nothing with a hash, token or URL in it.
- **Off means off:** the sender checks `shareRatings` before every run, and in Firefox also checks the data permission, so a setting without its permission sends nothing.

## Embedding scale

`CROWD-API.md` leaves this open: `vector` is 512 `int8` values in base64. Measure, don't guess. In `eval/`, quantize the 224 training embeddings at a few scales (127, 256 and 512, clamped to ±127), rerun leave-one-out, and pick the smallest loss. Write the scale into `votes.js` and `CROWD-API.md`.

- People with the picture check off can't rate today, so they can't vote. That doesn't change.

## Changes after review (these override anything above)

A review on 2026-11-01 found these problems. Where this section and the parts above disagree, this section wins.

**Hash only at rating time, only with sharing on.** This replaces "The hash" above. Hashing every picture adds a second full-size decode on every site for people who'll never vote, and it computes data the policy doesn't need. So `inspect()` doesn't change. When a rating is about to be queued, a new `hash` path fetches the URL with `credentials: 'omit'` and `cache: 'force-cache'`, runs `SlopHash.fromBlob`, and returns the hash, through the offscreen document in Chrome and the background page in Firefox. Guard it with `typeof SlopHash` and try/catch. If it fails, the rating still saves and no vote is queued. Step 5 decides how verdict matching gets hashes.

**One lock, no stale writes.**
- Every read-modify-write of `voteQueue`, plus clearing it and creating `voteSecret`, goes through one promise chain. Never hold it across the network.
- `voteSecret` is created through a single-flight promise, because two secrets would give one hash two tokens, which is a double vote.
- Each entry gets a sequence number. On `202`, remove an entry only if its number is unchanged, so a re-rating during a send survives.
- Re-read `shareRatings` right before each fetch, for votes and embeddings. A `storage.onChanged` listener aborts sends in flight and clears the queue under the lock.
- An in-memory `sending` guard stops an alarm and **Send now** overlapping. A resend after a worker restart is harmless, because the API replaces on hash and token.

**Replies, replacing the list above.**
- Build each body by picking fields explicitly, because the API's strict schema rejects extras such as `e` or `after`.
- `202` counts only if the body parses to `{accepted, needEmbedding: string[]}`. Ignore any hash in `needEmbedding` that wasn't in this batch, or doesn't match `^[0-9a-f]{16}$`.
- `400`: the API doesn't say which item failed, so split the batch and resend. Drop an item only when it's alone and the reply is a JSON `{error}`. After 3 batches in a row fail this way, stop sending and show "couldn't send, try updating the extension" in Settings. This stops a client bug or a proxy's reply from deleting everyone's votes.
- `413`: treat like `400`.
- Anything else, including `3xx`, `401`, `403`, `404`, `408`, `429`, `5xx` and network errors: keep everything and try at the next alarm.

**Firefox.**
- Raise `strict_min_version` to `140.0`, and `gecko_android` to `142.0`, because Mozilla's built-in consent doesn't exist below that.
- Use `data_collection_permissions: {required: ['none'], optional: ['websiteContent']}`.
- Call `permissions.request({data_collection: ['websiteContent']})` synchronously in a click handler, before any `await`, on its own, not on a `change` event.
- Detect Firefox separately, because a missing `data_collection` key from `permissions.getAll()` doesn't mean Chrome.
- Listen to `permissions.onRemoved`: a revoked permission turns sharing off and clears the queue.
- Before sending, check `permissions.contains({origins})`, because Firefox lets people install without site access, and the API has no CORS.

**Firefox may send a per-install ID.** Reports say extension POSTs carry `Origin: moz-extension://<uuid>`, fixed per profile, which would contradict "no voter ID". Don't assume either way. Run a real Firefox extension against a local server that prints request headers, and report exactly what's sent, in both browsers. If the UUID is there, strip it with `declarativeNetRequest` scoped to `api.hidetheslop.com`, if that's allowed for `Origin`. If it can't be stripped, stop and report it, because that's Kevin's decision.

**Settings.**
- Keep `shareRatings` out of `SLOP_DEFAULTS`, because `slopGetSettings()` reads sync and would always say false. Add `slopGetShare()` in `common.js`, reading local, and leave `data-key` off the control.
- Options has no `votes.js`, so the count and **Send now** go through a message to the background.
- "Forget them" also clears `voteQueue`, and doesn't rotate `voteSecret`, because re-rating would then add a second vote. The policy must say that sent votes can't be taken back.
- The welcome opt-in is unticked by default.

**Queue.**
- Store the `int8` base64 vector, about 700 bytes, rather than `e`, about 4.6 KB, because a failed `set` would lose the rating, and every local write wakes every content script. It's made from the raw CLIP embedding, never the retrained one.
- Batches are at most **5**, not 10.
- Skip queuing when `sender.tab.incognito`.

**Alarms.** Register `onAlarm` at the top level, and on every start call `alarms.get` and create it if missing, because alarms don't reliably persist. Add `alarms` to both manifests.

**Near-duplicates.** `vote_count` counts tokens across merged hashes, so one install rating copies 1 to 3 bits apart casts several votes, and could confirm a picture alone. Fix it in the client: keep a local list of hashes this install has sent, and reuse the earlier hash and token when a new hash is within 3 bits. This covers honest use, not a hostile client. Say so in `CROWD-API.md`.

**Embeddings.** The body is `{hashVersion: 1, modelVersion: 1, items: [{phash, token, vector}]}`.
