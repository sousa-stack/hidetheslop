## Schema

All in `src/db/schema.ts`. Drizzle has no built-in `bytea`, so use a `customType`.

```
enums: vote_label ('ai','real'); vote_source ('rated','hid');
       verdict_status ('pending','confirmed','disputed')
sequence: verdict_seq

hashes
  id            uuid primary key default gen_random_uuid()
  hash_version  smallint not null
  phash         bigint not null
  canonical_id  uuid null, references hashes(id) on delete cascade
  checked       boolean not null default false   -- near-duplicate check done
  first_seen    date not null default current_date
  band0         integer generated always as (((phash >> 48) & 65535)::integer) stored
  band1         integer generated always as (((phash >> 32) & 65535)::integer) stored
  band2         integer generated always as (((phash >> 16) & 65535)::integer) stored
  band3         integer generated always as ((phash & 65535)::integer) stored
  unique (hash_version, phash)
  index on (hash_version, bandN) for each band, and on canonical_id
  partial index on (first_seen, phash) where not checked

votes
  hash_id   uuid references hashes(id) on delete cascade
  token     char(32) not null    -- lowercase hex
  label     vote_label not null
  source    vote_source not null
  primary key (hash_id, token)

verdicts        -- roots only
  hash_id      uuid primary key references hashes(id) on delete cascade
  status       verdict_status not null
  label        vote_label null
  ai_weight    real not null
  real_weight  real not null
  vote_count   integer not null
  published    boolean not null default false
  seq          bigint null, indexed

embeddings
  hash_id        uuid references hashes(id) on delete cascade
  model_version  smallint not null
  vector         bytea not null   -- exactly 512 bytes
  primary key (hash_id, model_version)
```

**Why these ids and columns:** random ids and no vote timestamp, so stored rows don't show which votes arrived together. Sequential ids would put one person's batch in a neat run. Votes stay as long as their hash does: tokens can't be linked to each other, and keeping them stops double voting and lets verdicts be recounted.

**Two kinds of counting.** A *picture* is a root plus everything merged into it.
- **The embedding gate counts votes on the exact hash.** An honest install casts one vote per phash, so one person rating three near-identical copies can't open the gate, and neither can a private picture that collides with a popular one. "No embedding yet" still looks across the whole picture.
- **Verdicts count votes across the picture,** because reposts are the point. One person rating two near-identical copies counts twice, which is accepted.

## Behavior

**`lib/phash.ts`:** the wire format is 16 lowercase hex digits. Store with `BigInt.asIntN(64, ...)`, and read back with `BigInt.asUintN(64, ...)`, padded to 16 digits. Values with the top bit set must round-trip.

**`POST /v1/votes`:** strict schema. `hashVersion` is the literal 1. `votes` holds 1–50 items. `phash` matches `^[0-9a-f]{16}$`, `token` matches `^[0-9a-f]{32}$`.
- Reject with 400 a batch that has two different tokens for one phash. A real client never sends that, and it would let one request confirm a picture.
- In one transaction: dedupe the batch (the last vote wins for the same phash + token), insert missing hashes, and upsert votes on `(hash_id, token)`, updating `label` and `source`.
- Return `202 {accepted, needEmbedding}`. `needEmbedding` is the phashes in this request with at least `EMBEDDING_MIN_VOTES` votes on that exact hash and no embedding anywhere in the picture for `CURRENT_MODEL_VERSION`.
- Sort writes by `phash` to avoid deadlocks between batches.
- A foreign-key or deadlock failure from racing the aggregate job returns 503, and the client retries.

**`POST /v1/embeddings`:** strict schema: `{hashVersion, modelVersion, items: [{phash, token, vector}]}`. `hashVersion` is the literal 1, `modelVersion` must equal `CURRENT_MODEL_VERSION`, and `items` holds 1–50 entries. `vector` is base64 that decodes to exactly 512 bytes; reject anything else, using a canonical base64 check. Sort writes by `phash`.
- Store an item only if a vote exists with that phash and token, that exact hash has enough votes, and the picture has no embedding for that model. Use `on conflict do nothing`.
- Skip items that fail those checks instead of erroring. Return `202 {accepted}`, where `accepted` is the number of items received, so the response doesn't reveal what the server holds. Tests check rows, not this number.
- Concurrent writes or a later merge can leave two embeddings on one picture. That's accepted, and retraining dedupes.

**`GET /v1/verdicts`:** strict query: `since` (integer ≥ 0, default 0) and `hashVersion` (`z.coerce.number().pipe(z.literal(1))`).
- Rows with `seq > since`, ordered by `seq`, up to `VERDICTS_PAGE_SIZE` (10,000), for the given hash version. Fetch one extra row to set `more`.
- `add` holds root phashes with `published` true, `remove` those with it false. When `since` is 0, leave `remove` empty.
- `seq` is the last row's seq, or `since` when there are no rows.
- `Cache-Control: public, max-age=3600`. Turn off the `x-ratelimit-*` headers on this route, so they aren't cached.

**`GET /health`:** `SELECT 1`. `200 {status:'ok'}` or `503 {status:'unavailable'}`. Exempt from rate limiting. It never exposes the error text.

**App setup:**
- `trustProxy: 1`, because only Caddy talks to the API, and Caddy sets `X-Forwarded-For` to the real client (see Caddyfile).
- `bodyLimit` 64 KB, matching Caddy.
- `disableRequestLogging: true`, and logger serializers that remove `req` and `res` details.
- **Errors never log their contents.** Drizzle puts query parameters into `.message` and `.params`, so a logged query error would write phashes and tokens to disk. Log a fixed string, the route name and `err.cause?.code` (the SQLSTATE) only. Never log `.message`, `.stack` or the error object. The aggregate job follows the same rule. A 5xx must be logged this way; a 4xx needn't be.
- `@fastify/rate-limit` in memory, per `request.ip`: 60 requests an hour each for votes and embeddings, and 120 a minute for verdicts. These limits live in `config.ts`.
- A shared error handler returns `{error: <short code>}` and never echoes input. Validation errors return 400.

**`jobs/aggregate.ts`:** `runAggregate(db)`. Use `pg_try_advisory_xact_lock` in one transaction and return early if another run holds it. The steps are in order, as in CROWD-API.md:
1. For each unchecked hash, in `(first_seen, phash)` order: find the oldest root in that same order (`canonical_id is null`, `checked`, same `hash_version`) that shares a band and is within `MERGE_MAX_BITS` (3), using `bit_count((a.phash # b.phash)::bit(64))`. If found, set `canonical_id`. Set `checked` either way.
2. Consider only roots with `canonical_id is null and checked`, in this step and the next two. A hash committed after step 1 waits for the next run. Compute `vote_count`, `ai_weight` and `real_weight` across each root and its merged hashes. Recounting all roots is fine for now.
3. Upsert `verdicts`. Set the status and label from the rules. Compute `published`. When `published` differs from the stored value, or the row is new and published, set `seq = nextval('verdict_seq')`. A new row that isn't published keeps `seq` null.
4. Delete roots whose picture has fewer than `CONFIRM_MIN_VOTES` votes and whose `first_seen` is older than `LONE_HASH_DAYS`, cascading to merged hashes. A merged hash takes its root's fate.

`server.ts` runs this every `AGGREGATE_INTERVAL_MINUTES` (env, default 60; 0 turns it off) on an unref'd timer, logs a failure by the rule above, and stops cleanly on SIGTERM. Tests call `runAggregate` directly.

**`config.ts`:** `CONFIRM_MIN_VOTES = 5`, `CONFIRM_MIN_SHARE = 0.8`, `EMBEDDING_MIN_VOTES = 3`, `MERGE_MAX_BITS = 3`, `LONE_HASH_DAYS = 90`, `HID_WEIGHT = 0.5`, `CURRENT_MODEL_VERSION = 1`, `VERDICTS_PAGE_SIZE = 10000`, `MAX_BATCH = 50`.

**`env.ts`:** `DATABASE_URL` (required), `PORT` (default 3000), `HOST` (default `0.0.0.0`), `LOG_LEVEL` (default `info`), `AGGREGATE_INTERVAL_MINUTES`.

## Tests

Use `node:test` against a real Postgres from `TEST_DATABASE_URL`. Use `TRUNCATE` between tests, and refuse to run unless the database name contains `test`, because the tests wipe data. Use `app.inject` for routes. Every item below is a test:

- **phash:** round-trips, including a value with the top bit set.
- **votes:** accepted; same token replaces; same phash and token twice in one batch; two tokens for one phash rejected; 51 items rejected; bad hex rejected; `hashVersion: 2` rejected; an extra `url` or `key` field rejected on a vote and at the top level.
- **Embedding gate:** `needEmbedding` is empty at 2 votes and includes the hash at 3 on one hash. It stays empty for 3 votes spread across merged hashes, and once any hash in the picture has an embedding.
- **embeddings:** stored at 3 votes on the hash; skipped with 2; skipped for a token that didn't vote; skipped for a second embedding; 511 bytes and bad base64 rejected; wrong `modelVersion` rejected.
- **verdicts:** paging with `more`, `add`/`remove` on a later page, `remove` empty at `since=0`, the `Cache-Control` header, no `x-ratelimit-*` headers, a hash with the top bit set.
- **aggregate:** the 4/5 vote boundary; the 80% boundary for both labels; `disputed`; `hid` weights; `real` confirmed but not published; merging within 3 bits and not at 4; no chaining (A~B~C keeps C separate from A when C is 4+ bits from A); a vote flip unpublishes and bumps `seq`; a second run changes nothing, including `seq`; a held lock returns early; an unchecked hash with 5 votes gets no verdict row; lone hashes expire at 91 days and not at 89; confirmed ones don't expire; a child goes with its root.
- **Privacy:** capture log output through `logStream`, send requests with a recognisable `X-Forwarded-For` and phash, trigger a 202, a 400 and a 500, and assert the log contains neither. **Force the 500 with a real query failure, or a thrown `DrizzleQueryError` carrying the phash.** A plain `new Error()` wouldn't catch this bug. Rate limiting separates two clients by `X-Forwarded-For` through `trustProxy`.
- **Schema guard:** assert no table has a column named like `ip`, `url`, `user`, `email` or `voter`, and that `votes` has no date or time column.
- **health:** 200, and 503 with a broken database, without leaking the error.

**`scripts/test-local.sh`:** if `TEST_DATABASE_URL` is set, use it. Otherwise start a temporary cluster with `/opt/homebrew/opt/postgresql@18/bin`: `initdb` into `mktemp -d`, port 54329, localhost only, trust auth, `LC_ALL=en_US.UTF-8`, and `-c unix_socket_directories=''`. Without those last two, Postgres fails to start on this Mac. Run migrations and tests, and always stop it and delete the directory through a trap.

**`scripts/test-docker.sh`:** the same tests on the real versions, because Kevin's Mac runs Node 25. Use a temporary Docker network with a `postgres:18-alpine` container and a `node:26-alpine` container that copies `api/` from a read-only mount, runs `npm ci`, the migrations and the tests, and always removes what it created through a trap. Its database name must contain `test`.
